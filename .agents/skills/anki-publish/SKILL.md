# Anki Publish

Publish a plain, standard-text Front and a rendered Back, including code highlighting, tables, links, and local diagrams. **Keep normal Anki framing, base text size, and day/night text colors by default:** the existing template controls the top question, answer divider, left/right margins, and ordinary text presentation. The Back must inherit that size and text color, with a transparent outer background; do not pin ordinary text to the preview's black/white palette, copy a fixed preview size such as 14px, or hardcode 20px for every note. Apply theme adaptation to HTML text and its containers, preserving image/SVG colors and intentional code highlighting. Do not hide `{{FrontSide}}`, hide the divider, or reset Anki's page spacing. Use **VS Code's Markdown preview** as the reference for formatting within the Back's lesson, with relative heading sizes and scalable line heights, without importing its outer page gutters or adding a second title inside the answer. Raw Markdown or flattened plain text does not satisfy the Back's rendering requirements.

For an existing note, change only the intended content fields. Keep its note ID, card IDs, decks, tags, note type, templates, and review state. In particular, preserve due dates, intervals, ease, review/lapse counts, learning steps, suspension/burial, flags, filtered-deck state, and FSRS data. Anki may update ordinary modification/sync metadata as a consequence of editing content; this is not a scheduling change.

## Resolve the source and destination

1. Resolve the requested Markdown file(s), repository root, and applicable instructions. Publication alone does not call for rewriting the lesson or creating new visuals. If the user also requests content changes, use `anki-card-creation` first, and `svg-creation` only for changed diagrams.
2. Run the repository card validator with the selected or established `--mode simple` or `--mode complex`. Both current modes use title, navigation, teaching body, and Sources; headings do not identify the mode. **By default, use the text of the source's first level-one (`#`) heading as the Front in both modes**, displayed as ordinary Anki text. The Back is the rendered teaching body **including Sources**, without the opening title or repository navigation. Retain the template's normal top text/divider, internal links, and lesson formatting. One card or article becomes one note unless the user asks for a split. Preserve the existing destination field names; this does not retain a previous question-based Front selection over the current default. For legacy simple sources with Front/Back boundaries, validate a temporary normalized copy as described in [references/rendering.md](references/rendering.md#legacy-simple-sources); publication alone does not rewrite the source. See that reference for title extraction and explicit overrides.
3. Read [references/identity-and-decks.md](references/identity-and-decks.md) to resolve the Anki profile, exact deck, existing-note identity, and mapped fields. Search the collection before creating anything. Folder names are hints, not proven deck names. Existing notes keep their present decks during content updates.
4. Read [references/rendering.md](references/rendering.md) and prepare portable HTML and local media, preserving lesson formatting while inheriting the actual Anki base text size, day/night text colors, and normal card framing. Review the prepared front and back before writing.

## Connect and publish

Read [references/ankiconnect.md](references/ankiconnect.md) for setup, commands, payloads, and recovery. Prefer the bundled `scripts/anki_connect.py` helper over ad hoc mutation calls. It defaults to loopback and has no scheduler, deletion, tag-editing, or template-editing operations.

- A user request to publish authorizes creating the necessary new note and media, or updating the identified existing note. Do not ask for redundant confirmation. Creating this skill or merely editing a source does not authorize publishing any note.
- Anki must be open with the intended profile and AnkiConnect available. Diagnose first. If unavailable, finish the renderable output and state the specific missing dependency; do not silently install add-ons, expose a network listener, or modify the collection database. Follow through once the dependency is available.
- Record the concrete source, profile, deck, identity, field mapping, media names, and operation before mutation. Resolve genuine ambiguity before dependent writes; prepare everything independent while waiting.
- For an existing note, snapshot it immediately before updating and use `updateNoteFields` through the guarded helper. Do not delete/recreate, reimport a deck, change note type, edit templates/CSS, move cards, or invoke scheduling/review actions. Preserve every unmapped field and all tags. Reject cloze/conditional or otherwise card-generating structural changes rather than risk recreating cards. The helper supports ordinary unconditional front/back templates; unsupported templates require a separately assessed workflow, not bypassing the guard.
- For a new note, use the proven destination and one dedicated ordinary front/back template, with an immutable `SourceId` for identity. Reuse a compatible dedicated note type; create one only when needed. Never edit a shared note type's styling to publish one lesson. Write styles inside the scoped content fields.
- Store media under content-hash filenames, verify bytes, then write the note. Do not overwrite or delete another note's media. An unchanged publication performs no mutation.

## Verify and report

Read the stored fields back and inspect the actual Anki **Browse → Preview** front and back. Do not grade a card to test it. Check that ordinary Back text, lists, table cells, inline code and code blocks use the destination note type's base text size; verify descendant styles have not reintroduced a fixed preview size. Headings and line heights must scale with that base. Check that the Front matches the first level-one heading (or the user's explicit override) and uses ordinary text styling, the template's normal top text/divider and left/right margins remain, and the Back field adds neither a duplicate opening title nor extra preview gutters. Verify ordinary text and links in both day and night mode, including nested emphasis and table cells; check code contrast without recoloring images or SVGs. Check heading hierarchy, tables, images, links, and long-article scrolling against the source. Preview every affected card of a multi-card note. If GUI access is unavailable, report that visual verification is pending instead of claiming complete fidelity.

For updates, compare before/after note and card identities, non-content fields, deck placement, templates, tags, every exposed scheduling property, and complete review-log rows. The helper returns its checked properties. Standard AnkiConnect may not expose flags, original due/deck, or all FSRS fields: leave them untouched by using only the content API, but do not claim they were independently compared. Never attempt to repair a mismatch by writing scheduling values. Stop on a mismatch and preserve the snapshots for diagnosis.

Persist the source mapping only after reconciliation/verification. Report the source, deck, created/updated/unchanged result, note ID, and actual verification coverage. Distinguish intended preservation from properties that the installed API could verify. If a write outcome is uncertain, reconcile it before retrying; never blindly replay note creation.
