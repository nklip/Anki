# Primary Key Generation in Jakarta Persistence and Hibernate

*Updated for Jakarta Persistence 3.2 and Hibernate ORM 6.x/7.x.*

Jakarta Persistence defines five primary key generation strategies.  
A sixth option — assigning the key yourself — is often the right answer and is covered at the end.

| Strategy | Mechanism | Batching | Notes |
|---|---|---|---|
| `AUTO` | Provider chooses, based on the PK type | depends | Default; behaviour differs by database |
| `IDENTITY` | Auto-increment / identity column | ❌ disabled | Simplest, worst for bulk writes |
| `SEQUENCE` | Database sequence | ✅ | Preferred where sequences exist |
| `TABLE` | Table simulating a sequence | ✅ | Legacy; avoid |
| `UUID` | RFC 4122 UUID generated by the provider | ✅ | Added in Jakarta Persistence 3.1 |

## AUTO

`GenerationType.AUTO` is the default when you write a bare `@GeneratedValue`.

Since Jakarta Persistence 3.1 its behaviour depends on the type of the primary key attribute, not only on the dialect:

- Key of type `UUID` or `String` → equivalent to `GenerationType.UUID`
- Key of type `Long`, `Integer`, `long`, `int` → provider picks among `TABLE`, `SEQUENCE`, `IDENTITY`

Hibernate's pick for numeric keys follows the dialect:

| Database | Hibernate 6/7 resolves `AUTO` to |
|---|---|
| PostgreSQL, Oracle, H2, DB2, SQL Server 2012+ | `SEQUENCE` |
| MySQL, MariaDB | `TABLE` — these engines have no sequences |

> ⚠️ **The MySQL trap.** On MySQL and MariaDB, `AUTO` degrades to the `TABLE` generator, the slowest strategy available. On these databases, always specify `IDENTITY` explicitly rather than relying on `AUTO`.

> ⚠️ **Hibernate 5 → 6 migration.** Hibernate 5 used a single shared `hibernate_sequence` for all entities. Hibernate 6 switched to entity-specific sequences named `<table>_SEQ`. Schemas created under Hibernate 5 will fail at startup after upgrading unless the new sequences are created or the old name is configured explicitly.

Because the resolution is both type-dependent and dialect-dependent, `AUTO` is a poor choice for anything but prototypes. Name the strategy you actually want.

## IDENTITY

```java
@Id
@GeneratedValue(strategy = GenerationType.IDENTITY)
private Long id;
```

Relies on an auto-increment column; the database assigns the value during the `INSERT`. From the database's perspective this is highly efficient — identity columns are well optimised and no extra round trip is needed.

The cost is on the Hibernate side. A managed entity must have an identifier, so Hibernate has to execute the `INSERT` immediately at `persist()` time rather than deferring it to flush. Two consequences:

1. **JDBC batching is silently disabled for these entities.** This remains true in Hibernate 6.x and 7.x. Setting `hibernate.jdbc.batch_size` has no effect on inserts of `IDENTITY` entities.
2. **Write ordering is lost.** Hibernate can no longer reorder or group statements at flush time, which also weakens its ability to avoid constraint-violation ordering problems.

Hibernate retrieves the key via `Statement.getGeneratedKeys()`, or via `INSERT … RETURNING` on dialects that support it. Hibernate 6.5 extended the same mechanism to arbitrary generated columns, halving round trips for entities with `@Generated` properties — but this does not re-enable insert batching for `IDENTITY`.

**Use it when:** you're on MySQL/MariaDB, or write volume is low and you value schema simplicity.

## SEQUENCE

```java
@Id
@GeneratedValue(strategy = GenerationType.SEQUENCE, generator = "book_seq")
@SequenceGenerator(name = "book_seq", sequenceName = "book_seq", allocationSize = 50)
private Long id;
```

The preferred strategy wherever the database supports sequences. Hibernate can obtain the identifier before the insert, which preserves write-behind, statement reordering, and JDBC batching.

It costs an extra `SELECT` per allocation — but per allocation, not per row, and that distinction is where most of the tuning lives.

### `allocationSize` is the whole game

`allocationSize` tells Hibernate how many identifiers it may hand out per sequence call. With `allocationSize = 50`, one `nextval` covers fifty inserts. Hibernate applies a pooled optimizer automatically whenever `allocationSize > 1`.

> ⚠️ **`allocationSize` must match the sequence's `INCREMENT BY`.** This is the most common production bug in this area. If the sequence increments by 1 but Hibernate believes it may allocate 50, you get duplicate key violations or negative identifiers. Either:

```sql
CREATE SEQUENCE book_seq START WITH 1 INCREMENT BY 50;
```

…or set `allocationSize = 1` and accept one round trip per insert.

Note the defaults differ: the JPA specification's default `allocationSize` is 50, while a hand-written `CREATE SEQUENCE` defaults to `INCREMENT BY 1`. Schema generation tools get this right; hand-maintained DDL and Flyway/Liquibase scripts frequently do not.

### Expect gaps

Allocated-but-unused identifiers are discarded when the application shuts down or a transaction rolls back. Sequence-generated keys are unique and monotonic, not contiguous. Never expose them as invoice numbers or anything requiring gapless ordering.

**Use it when:** single database, server-side inserts, you control write ordering, PK is internal, Storage and index density matter

## TABLE

```java
@Id
@GeneratedValue(strategy = GenerationType.TABLE, generator = "book_gen")
@TableGenerator(name = "book_gen", table = "id_generator",
                pkColumnName = "seq_name", valueColumnName = "seq_value",
                allocationSize = 50)
private Long id;
```

Simulates a sequence by storing the current value in a row of an ordinary table, read and updated under a row lock. Because that lock is held across the read and the update, concurrent identifier requests serialise — under write-heavy load this becomes the application's bottleneck.

Hibernate does apply the same pooled optimizer here, and modern implementations run the update in a separate transaction rather than holding the lock for the caller's whole transaction. It is still markedly slower than a real sequence.

**Use it when:** essentially never by choice. Its main relevance today is that it's what `AUTO` silently selects on MySQL and MariaDB.

## UUID

Added in Jakarta Persistence 3.1; supported by Hibernate 6.2+.

```java
@Id
@GeneratedValue(strategy = GenerationType.UUID)
private UUID id;
```

The identifier is generated in the JVM, so no database round trip is required and batching works. This makes it attractive for distributed systems, offline-capable clients, and merge-replication scenarios where a central allocator is impractical.

The specification does not mandate a UUID version, and that matters:

> ⚠️ **Random (v4) UUIDs fragment B-tree indexes.** Inserts land at random points in the primary key index, causing page splits and poor cache locality. On a large table this can cost significantly more than the round trip a sequence would have needed.

If you do need UUIDs, don't use v4. Hibernate 7 now offers time-ordered styles directly:

```java
@Id @GeneratedValue
@UuidGenerator(style = UuidGenerator.Style.VERSION_7)
private UUID id;
```

Check your Hibernate version's `@UuidGenerator` for UUIDv7 support, which is the current standard answer for time-ordered UUIDs.

Also consider storage: 16 bytes as `uuid`/`BINARY(16)` versus 36 as `VARCHAR(36)`. The difference compounds across every foreign key and index in the schema.

**Use it when:** ID must exist before insert (offline clients, event sourcing), Multi-master / merge replication, cross-DB merges, Distributed writers with no central allocator, you're sharding and can't coordinate ranges

## The sixth option: assign it yourself

`@GeneratedValue` is not mandatory. Generating the key in the application — a UUIDv7, a Snowflake ID, or a genuine business key — gives you the identifier before persistence with no coordination at all.

One caveat with Spring Data JPA: `save()` cannot distinguish a new entity from a detached one when the ID is pre-assigned, so it issues a `SELECT` before every `INSERT`. Implement `Persistable` to avoid it.
