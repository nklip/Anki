# AOT vs. JIT

## Front

What are JIT and AOT compilation in modern Java?

Explain:

- How ordinary HotSpot JIT compilation works.
- How GraalVM Native Image differs from JVM execution.
- Why runtime profiling benefits JIT compilation.
- How profile-guided optimization helps Native Image.
- How Project Leyden combines AOT knowledge with the JVM and JIT.
- What changed in JDK 24, JDK 25, and JDK 26.

## Back

There are two ways of compiling a Java application: using **Just-in-Time compilation (JIT)** or **Ahead-of-Time compilation (AOT)**.

**JIT is still the normal/default way Java runs.** AOT is increasingly used to improve startup and memory, and Java is moving toward a hybrid JIT + AOT model.

The first is the default mode, and it is used by the Java HotSpot Virtual Machine to translate bytecode into machine code at runtime.

The latter is supported by GraalVM Native Image and allows statically compiling bytecode directly into machine code at build time.

![AOT versus JIT comparison](svg/aot_vs_jit.svg)

## JIT today

Default Java applications still run on the JVM using Just-in-Time compilation.

### JIT flow

![Java execution flow with JIT](svg/aot_vs_jit_jit_flow.svg)

```text
.java source
    ↓ javac
.class bytecode
    ↓
JVM interpreter
    ↓
JIT detects hot code
    ↓
optimized native machine code
```

HotSpot can observe what the program actually does at runtime and optimize frequently executed code based on that information. This is one reason JIT remains particularly strong for long-running server applications.

GraalVM's documentation also notes that runtime profiling gives JIT an optimization advantage because it can see actual branch frequencies, method usage, and other runtime behavior.

### Traditional JIT warmup

![Traditional JIT warmup](svg/aot_vs_jit_traditional_jit_warmup.svg)

At the beginning of a normal run, the JVM has little application-specific profiling information. It must execute code, collect profiles, identify hot methods, and then compile optimized native code. The application reaches peak performance after this warmup period.

## AOT today

There are now two different things people may mean by **“AOT Java.”**

![Modern Java execution paths](svg/aot_vs_jit_modern_java_execution_paths.svg)

### 1. GraalVM Native Image — full native AOT

GraalVM Native Image can compile a Java application into a platform-specific native executable:

![GraalVM Native Image AOT flow](svg/aot_vs_jit_graalvm_native_image.svg)

For example:

```text
my-service
```

instead of:

```bash
java -jar my-service.jar
```

Modern Native Image also supports **profile-guided optimization (PGO)**, where you run a representative workload first and feed the profile into the AOT compiler. This lets AOT recover some of the runtime information that normally gives JIT its advantage.

```text
Build instrumented native executable
        ↓
Run representative workload
        ↓
Collect profile
        ↓
Build optimized native executable with that profile
```

### 2. OpenJDK / Project Leyden — AOT-assisted JVM

This is arguably the most interesting recent development.

OpenJDK is introducing AOT techniques **without abandoning the JVM or JIT**.

So instead of **JIT vs. AOT**, the direction is increasingly:

![Hybrid AOT and JIT flow](svg/aot_vs_jit_hybrid.svg)

```text
AOT knowledge + JVM + JIT
```

Project Leyden lets the JVM save useful work from previous runs and reuse it later.

### JDK 24: Ahead-of-Time Class Loading & Linking

JDK 24 introduced **Ahead-of-Time Class Loading & Linking**, which lets HotSpot cache classes that were already loaded and linked during a training run.

```text
Training run
    ↓
record classes that were loaded and linked
    ↓
create AOT cache
    ↓
reuse the cache in later JVM runs
```

The application still runs on HotSpot. The cache shifts repeated class-loading and linking work to an earlier phase so subsequent starts can be faster.

### JDK 25: Ahead-of-Time Method Profiling

JDK 25 added **Ahead-of-Time Method Profiling**.

Instead of starting with zero runtime knowledge:

![Traditional JIT startup without a saved profile](svg/aot_vs_jit_traditional_jit_warmup.svg)

HotSpot can reuse profiles from an earlier run:

![Profile-guided JVM startup](svg/aot_vs_jit_profile_guided_jvm_startup.svg)

That feature was delivered in JDK 25. It enables the JIT compiler to generate optimized native code sooner because useful method-execution profiles are already available at startup.

This remains a **JVM + JIT** execution model. The profile is collected ahead of time, but optimized machine code can still be generated by the JIT in the new run.

### JDK 26: AOT cache with any garbage collector

JDK 26 further expanded the AOT cache so it can work with any garbage collector, including ZGC.

The cache can store Java objects in a neutral, GC-agnostic representation. This removes the previous incompatibility between cached objects and collectors whose object-reference representation differs from the traditional HotSpot heap layout.

## The modern picture

| Execution model | When native code is produced | Runtime profiling | JVM required at runtime | Typical strengths |
|---|---|---|---|---|
| HotSpot JIT | During application execution | Collected during the current run | Yes | Peak throughput and adaptive optimization |
| GraalVM Native Image | During the build | Optional PGO from a training workload | No ordinary JVM process | Fast startup, smaller runtime footprint, native executable |
| Leyden AOT-assisted JVM | Some JVM work is cached before production; JIT still compiles at runtime | Profiles can be reused from a training run | Yes | Faster startup and warmup while retaining JVM dynamism and JIT |

## Key distinction

**GraalVM Native Image AOT** and **OpenJDK's AOT cache** are not the same thing:

- Native Image produces a standalone platform-specific executable.
- Project Leyden's AOT cache accelerates a later HotSpot JVM run.
- The Leyden path retains the JVM, dynamic behavior, and JIT compilation.
- Modern Java therefore increasingly combines AOT preparation with adaptive JIT optimization.
