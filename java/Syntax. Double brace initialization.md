# Syntax. Double-Brace Initialization in Modern Java

## Front

What is **double-brace initialization** in Java?

How does it work, why is it discouraged in modern Java, does it always retain its enclosing object, and what should be used instead?

## Back

**Double-brace initialization is not a special Java feature.** It combines two existing language features:

1. An **anonymous subclass** — the outer braces.
2. An **instance initializer** — the inner braces.

```java
Map<String, Integer> scores = new HashMap<>() {{
    put("Alice", 10);
    put("Bob", 20);
}};
```

The object is **not an ordinary `HashMap` instance**. It is an instance of an anonymous class that extends `HashMap`.

Conceptually, the code resembles:

```java
final class GeneratedMap extends HashMap<String, Integer> {
    {
        put("Alice", 10);
        put("Bob", 20);
    }
}

Map<String, Integer> scores = new GeneratedMap();
```

The actual anonymous class has no source-level name. The compiler generates a class file with a name similar to `Example$1`.

## What the two pairs of braces mean

### First pair: anonymous subclass

```java
new HashMap<String, Integer>() {
    // Anonymous-class body
}
```

This creates a new subclass of `HashMap` and then creates an instance of it.

### Second pair: instance initializer

```java
{
    put("Alice", 10);
    put("Bob", 20);
}
```

An instance initializer runs as part of object construction, after the superclass constructor has run and before construction finishes.

The syntax only looks like a convenient collection literal:

```text
new HashMap<>() {{ entries }}
                  │         │
                  └ initializer inside an anonymous subclass
```

Java does not treat it as a collection literal or builder.

## Why it is discouraged

### 1. It creates an anonymous class

Every double-brace expression creates a subtype:

```java
Map<String, Integer> normal = new HashMap<>();

Map<String, Integer> doubleBrace = new HashMap<>() {{
    put("Alice", 10);
}};

System.out.println(normal.getClass() == HashMap.class);      // true
System.out.println(doubleBrace.getClass() == HashMap.class); // false
```

Each **source-code occurrence** produces a separate anonymous class. Repeated execution of the same occurrence creates more instances of that class; it does not generate a new class on every execution.

The additional class normally has small overhead, but the class identity, class metadata, generated bytecode, and initialization are unnecessary for ordinary data construction.

### 2. It cannot be used with final classes

Double-brace initialization depends on inheritance, so it cannot subclass a final type:

```java
final class Settings {}

// Does not compile: Settings cannot be subclassed
Settings settings = new Settings() {{
}};
```

Records are implicitly final, so they cannot be initialized this way either. Records also cannot declare instance initializers.

### 3. It can capture surrounding state

If the anonymous class uses an enclosing instance member, an explicit `Outer.this`, or a local variable, that state must be captured:

```java
final class UserRegistry {
    private final String owner = "Alice";

    Map<String, String> createMap() {
        return new HashMap<>() {{
            put("owner", owner); // Uses the enclosing UserRegistry
        }};
    }
}
```

The returned map can then keep the `UserRegistry` instance reachable for as long as the map remains reachable.

The same principle applies to effectively final local variables:

```java
String owner = loadOwner();

Map<String, String> map = new HashMap<>() {{
    put("owner", owner); // Captured local value
}};
```

This can increase object lifetime and memory retention unexpectedly.

### Modern `javac` nuance: an outer reference is not always stored

The traditional warning says that every anonymous inner class permanently stores a reference to its enclosing object. That is too broad for current `javac`.

Since **JDK 18**, `javac` can omit the synthetic enclosing-instance field when the inner or anonymous class does not use any enclosing-instance state:

```java
final class Example {
    Map<String, Integer> createMap() {
        return new HashMap<>() {{
            put("answer", 42); // Does not use Example.this
        }};
    }
}
```

With a current `javac`, this anonymous object normally does not need to retain the `Example` object after construction.

However:

- Referencing enclosing instance state still requires capture.
- Referencing a local value still requires that value to be captured.
- Older compiler output may still contain an unused enclosing-instance field.
- Compiler-generated fields are implementation details and should not be relied upon by application code.

Therefore, **“always leaks the outer object” is outdated**, but **“can capture and retain surrounding state” remains correct**.

### 4. Serialization becomes fragile

`HashMap` and `ArrayList` are serializable, so their anonymous subclasses can also enter Java serialization. The serialized form can then depend on:

- A compiler-generated anonymous class name such as `Example$1`.
- Captured fields.
- The enclosing object when it is actually captured.
- Compiler implementation details.

If a captured enclosing object is not serializable, serialization can fail with `NotSerializableException`. If it is serializable, a much larger object graph than expected may be serialized.

Even without capture, persisting an anonymous implementation class creates a brittle dependency on generated class structure. Do not use double-brace objects as long-lived serialized data.

### 5. It can surprise frameworks and reflection-based code

Some serializers, ORM tools, dependency-injection containers, mappers, and reflection utilities care about the concrete runtime class, constructors, declared fields, or stable class names.

They may observe an anonymous subtype instead of the requested collection implementation:

```java
System.out.println(scores.getClass().isAnonymousClass()); // true
```

Well-written code normally programs to `Map`, `List`, or `Set`, but exact-class assumptions still occur at framework boundaries.

### 6. It puts behavior inside construction

An instance initializer runs while the object is being constructed. It can call methods on `this`, invoke overridable methods, throw exceptions, or expose the partially constructed object.

```java
Map<String, Integer> map = new HashMap<>() {{
    register(this); // `this` escapes during construction
    put("answer", 42);
}};
```

This is a general construction-time hazard, not something needed to initialize a collection.

## Does it break `equals()`?

Not automatically.

The standard `List`, `Set`, and `Map` equality contracts are content-based, so an anonymous `HashMap` subclass normally compares equal to an ordinary map containing the same mappings:

```java
Map<String, Integer> first = new HashMap<>();
first.put("answer", 42);

Map<String, Integer> second = new HashMap<>() {{
    put("answer", 42);
}};

System.out.println(first.equals(second)); // normally true
```

The problem is not the standard `Map.equals()` contract. The problem is code that uses exact concrete-class checks, reflection, generated metadata, or subclass-specific state.

## Preferred modern alternatives

### Unmodifiable map: `Map.of()`

```java
Map<String, Integer> scores = Map.of(
        "Alice", 10,
        "Bob", 20
);
```

This is concise and creates an unmodifiable map.

Important properties:

- The map cannot be modified after creation.
- `null` keys and values are rejected.
- Duplicate keys are rejected.
- Iteration order is unspecified.

`Map.of()` provides overloads for up to ten key-value pairs.

### Larger unmodifiable map: `Map.ofEntries()`

```java
Map<String, Integer> scores = Map.ofEntries(
        Map.entry("Alice", 10),
        Map.entry("Bob", 20),
        Map.entry("Carol", 30)
);
```

Use `Map.ofEntries()` when the fixed `Map.of()` overloads are not convenient.

### Mutable map initialized from fixed data

```java
Map<String, Integer> scores = new HashMap<>(Map.of(
        "Alice", 10,
        "Bob", 20
));

scores.put("Carol", 30);
```

The resulting `HashMap` is mutable. The intermediate `Map.of(...)` still rejects `null` keys, `null` values, and duplicate keys.

### Mutable map with `null`, ordering, or step-by-step construction

```java
Map<String, Integer> scores = new LinkedHashMap<>();
scores.put("Alice", 10);
scores.put("unknown", null);
scores.put("Bob", 20);
```

This is explicit, easy to debug, and creates the concrete class that the code says it creates.

Use `LinkedHashMap` when insertion order matters or `HashMap` when it does not.

### Lists and sets

Unmodifiable collections:

```java
List<String> names = List.of("Alice", "Bob");
Set<String> roles = Set.of("ADMIN", "USER");
```

Mutable collections:

```java
List<String> names = new ArrayList<>(List.of("Alice", "Bob"));
Set<String> roles = new HashSet<>(Set.of("ADMIN", "USER"));
```

For an existing mutable collection, a bulk operation can also be clear:

```java
List<String> names = new ArrayList<>();
Collections.addAll(names, "Alice", "Bob");
```

### Complex or conditional construction

Use ordinary statements or a helper method:

```java
static Map<String, Integer> createScores(boolean includeGuest) {
    Map<String, Integer> scores = new HashMap<>();
    scores.put("Alice", 10);
    scores.put("Bob", 20);

    if (includeGuest) {
        scores.put("Guest", 0);
    }

    return scores;
}
```

If callers must not modify the result:

```java
return Map.copyOf(scores);
```

`Map.copyOf()` also rejects `null` keys and values.

## Quick comparison

| Construction | Mutable? | Anonymous subclass? | Allows `null`? | Recommended? |
|---|---:|---:|---:|---:|
| `new HashMap<>() {{ ... }}` | Yes | Yes | Yes | Generally no |
| `Map.of(...)` | No | No | No | Yes, for fixed data |
| `Map.ofEntries(...)` | No | No | No | Yes, for larger fixed data |
| `new HashMap<>(Map.of(...))` | Yes | No | Not in initial fixed data | Yes |
| `new HashMap<>(); put(...)` | Yes | No | Yes | Yes |
| `Map.copyOf(existing)` | No | No | No | Yes, for an unmodifiable result |

## Common misconceptions

### “It is just shorter syntax for several `put()` calls”

No. The `put()` calls are made from an instance initializer in a new anonymous subclass.

### “It creates a new class every time the line runs”

No. One anonymous class is normally generated for each source occurrence; every execution creates another object of that generated class.

### “It always stores `Outer.this`”

Not with current `javac` when enclosing-instance state is unused. Since JDK 18, the compiler can omit the unused field. Capture still occurs when surrounding state is referenced.

### “It is immutable because it is initialized inline”

No. A double-brace `HashMap` remains mutable unless additional mechanisms prevent mutation.

### “Declaring the variable as `Map` removes the anonymous class”

No. The declared reference type does not change the runtime object:

```java
Map<String, Integer> map = new HashMap<>() {{
    put("answer", 42);
}};
```

The runtime object is still an anonymous `HashMap` subclass.

## When is it acceptable?

It may appear in small, disposable tests where:

- The object never crosses a serialization or framework boundary.
- Capturing surrounding state is understood.
- The extra anonymous class is irrelevant.
- The team explicitly accepts the idiom.

Even there, modern factory methods or ordinary initialization are usually just as readable and less surprising.

Avoid double-brace initialization in production APIs, persisted objects, framework-facing models, and long-lived collections.

## Interview summary

> Double-brace initialization combines an anonymous subclass with an instance initializer. It is discouraged because it creates an unnecessary subtype, may capture surrounding state, complicates serialization and reflection, cannot work with final classes, and executes arbitrary code during construction. Modern `javac` no longer always stores an unused enclosing-object reference—the field can be omitted since JDK 18—but capture still occurs when outer or local state is used. Prefer `Map.of`, `Map.ofEntries`, `List.of`, `Set.of`, mutable copies, or ordinary collection-building statements.
